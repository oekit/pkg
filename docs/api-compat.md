# API 兼容策略与生命周期分级

> 写给两拨人：**消费方开发者**——升级 pkg 前想知道「哪些包敢随便升、哪些要读
> CHANGELOG」；**改本仓的 AI 代理与维护者**——想改一个包之前先知道「这个
> 级别允许我改什么」。
>
> 本文件是 `api-lifecycle.yaml` 清单的**口径书**：分级的语义在这里定义，
> 清单登记事实，机器门禁保证两边不漂。三者缺一不可——只有文档没有清单，
> 分级半年后漂移；只有清单没有文档，「什么算 breaking」没有裁决依据。
>
> 口径与 `goagent-kernel` 的同名文档同源（同一套分级词表与判定规则），
> 但**各自成册**——两仓的包集合、breaking 纪律与发版节奏都不同，
> 共用一份文档会让两边的裁决依据互相污染。

## 为什么要机器可判

本仓发版历史里已有多轮 BREAKING：`cache` 的 Checker 构造期 fail-fast、
`encoding` 五入口分族、`jsonrepair` 的围栏口径单源化、`pagination` 的
WalkEach 形参带 ctx、`urlguard` 的 `WithAllowedSchemes` 改替换语义……
每次都靠单篇 CHANGELOG 承担全部迁移说明——**没有机器可判的机制**，
意味着「文档里写了但代码里没改」没有任何信号。

机制面因此由三件东西组成，各管一段漂移：

| 件 | 管什么漂移 |
|---|---|
| 包注释标记（`// 生命周期: <级别>`） | 分级跟着包走（godoc、代码评审现场都看得见） |
| `api-lifecycle.yaml` 清单 | 全仓一张总表：定级 + 理由 + 定级版本，机器可读 |
| 门禁（判据脚本住治理仓 matrix-tools） | 清单 ↔ 包注释 ↔ 生产包集合，三处一致才绿 |

### 门禁为什么不住在本仓

pkg 是**零第三方依赖仓**（CI 强制 `go list -m all` 只允许本模块一行），
解析 YAML 需要 `gopkg.in/yaml.v3`——门禁若住在本仓就会破这条红线，
而这条红线是本仓「一个 import 即用、零捆绑」承诺的机器形态。

⇒ 判定逻辑放治理仓 `matrix-tools`（Python + pyyaml），本仓只留声明面
（清单 + 包注释标记 + 本文件），**消费方的依赖图不受任何影响**。
这与 `oekit/oekit` 的 BOM 新鲜度门禁是同一范式：「判据脚本住在治理仓，
本仓只有产物」。

## 分级判定规则

**breaking 的定义（四类，命中任何一类即 breaking）：**

1. **改签名**——已有导出函数/方法的参数、返回值、error 类型变化；
   接口新增方法也算（实现方被迫改代码；Stable 接口扩方法的唯一合法形态
   是「新方法 + 零值默认实现」）；
2. **改语义**——签名不变但可观测行为变了：判定结论变化、错误类型变化、
   并发/时序保证变化、输入的合法域变化；
3. **改默认值**——零值语义、缺省配置、缺省超时/阈值变化（调用方一行不改
   却拿到不同行为的，全部算）；
4. **删导出符号**——删除或改名任何导出类型/函数/变量/常量，包括把导出
   符号降级为未导出。

**不是 breaking 的：** 新增导出符号、新增包、修 bug（行为向文档
已声明的语义收敛）、新增错误值（新增错误值不改变既有成功路径）。

## 三档级别

| 级别 | 允许什么 | 承诺什么 |
|---|---|---|
| **Stable** | 只允许 additive：新增导出符号、新增方法（且给零值默认实现）、新增错误值 | 上面四类 breaking 一律不得发生。改既有导出面 ⇒ 先在本文件与清单里降级为 Experimental，并在 CHANGELOG 写 BREAKING 段 |
| **Experimental** | 可随时改、删、拆 | **不承诺任何兼容**，升级风险自负 |
| **Deprecated** | 本身仍按 Stable 兼容 | 必须给替代符号与迁移路径；删除只发生在 minor 版本边界，且 CHANGELOG 必须带 BREAKING 段 |

### 定级不靠拍脑袋

每一档定级背后有两把尺：

1. **实测下游消费方计数**——该包在 oekit 矩阵与跨 org 仓里被 import 的处数。
   消费方为零的包没有「必须兼容」的既成事实，先标 Experimental，
   有下游接手时再转 Stable（这正是「已上架待取货」件的处置口径）；
2. **历史 breaking 次数与判据成熟度**——判据还在随宿主反馈调整的包，
   标 Stable 就是给自己套一个兑现不了的枷锁。

**注意**：本仓处于 0.x，SemVer 允许 minor 内 breaking。分级承诺的是
「什么时候可以改」，不是「永远不能改」——降级（Stable → Experimental）
本身是允许的合法动作，前提是走完本文件的降级流程并公告。

## 降级流程（Stable → Experimental）

1. 清单里该包的 `level` 改 Experimental，`reason` 写明「为什么现在不能
   继续承诺」；
2. 包注释标记同步改（门禁会校验两者一致）；
3. 本文件补一段该包的降级说明；
4. CHANGELOG 写明降级版本与影响面。

**降级不是甩锅**——降级后仍要尽量给消费方留迁移窗口；只有在判据本身
正在重构、任何中间态都会误导调用方时，才允许直接改行为并公告。

## 新增包的定级纪律

新增生产包 ⇒ 清单同步登记 + 包注释打标记。定级默认从 **Experimental**
起步：有真实下游消费方、且判据面经至少一次宿主接入验证后，再申请转 Stable。
理由是「新包的 API 形状通常在第一次真实接入后才会收敛」——先承诺再违约，
比先不承诺更伤消费方。

## 怎么查一个包现在什么级别

```bash
# 清单里的定级与理由
grep -A3 'pkg: <包名>' api-lifecycle.yaml

# 包注释里的标记（godoc 里也看得见）
grep -rn '生命周期[:：]' <包名>/
```
